## 1. 背景与目标

### 1.1 业务背景

OpenHouse（开放日）是房源营销的重要形式：把房子在特定时段开放给意向客户实地参观。一场开放日活动涉及**活动组织（时间、地点、名额、参观路线）、报名收集、资格审核、现场签到、效果复盘**五个环节，链条长、参与方多（管理员、参与者、业主、现场人员）。

本系统承载这条链条的全程数字化。

### 1.2 现状问题（痛点 → 需求来源）

| 编号 | 痛点 | 业务影响 | 对应需求 |
|---|---|---|---|
| P1 | 活动组织靠 Excel + 群接龙，信息散乱易错 | 活动信息不同步，名额与时段失控 | FR-1.x 活动管理 |
| P2 | 报名信息格式不一、真实性无法核验 | 现场到访率不可预测，资源浪费 | FR-2.x 报名系统 + FR-3.x 审核机制 |
| P3 | 现场签到靠纸笔，无法实时核销 | 排队、漏登、数据缺失 | FR-4.x 签到功能 |
| P4 | 效果统计靠事后手工汇总 | 复盘滞后，口径不一 | FR-5.x 数据统计 |
| P5 | 活动信息录入繁琐（楼盘/面积/价格手填） | 创建成本高，易填错 | FR-6.x 房源集成（v5） |
| P6 | 筹备进度黑盒 | 活动临近才发现物料/信息缺口 | FR-7.x AI 筹备助手 |

> 痛点来源：v1 初始需求原文六大核心能力（★ 实测）+ v5 房源集成需求（★ 实测）+ v24 前台 AI 筹备助手入口（★ 实测）。

### 1.3 产品目标

| 层级 | 目标 | 衡量指标 | 目标值 | 说明 |
|---|---|---|---|---|
| 业务 | 提升活动到访兑现 | **活动到访率（签到率）** | 基线待补（TBD） | 北极星指标，见 8.1 |
| 业务 | 降低审核等待 | 报名审核时长 P90 | ≤ 4 小时（TBD） | 需先取基线 |
| 用户 | 降低创建成本 | 创建一个活动所需时长 / 手填字段数 | 房源字段 0 手填（v5 已达成） | 活动标题/地点/描述自动填充 |
| 用户 | 报名体验 | 报名漏斗完成率（提交/PV） | 环比提升 | 见 8.2 |
| AI | 筹备透明化 | AI 筹备助手使用率 / 诊断采纳率 | TBD | v24 已有入口 |

### 1.4 非目标（本期明确不做）

- 不做线上支付与收费报名
- 不做活动内容 CMS（富媒体营销页搭建）
- 不做参与者社交与互动社区
- 不做跨平台日历同步（ics/日历订阅，可列入后续）

## 2. 用户与角色

### 2.1 角色定义

| 角色 | 角色说明 | 核心诉求 | 主要使用模块 |
|---|---|---|---|
| 活动管理员 | 创建/发布活动、审核报名、现场组织 | 高效发布、快速审核、看清数据 | 活动管理、活动筹备（报名管理/审核列表）、现场管理（签到管理/实时动态）、会后管理（数据统计/活动报告） |
| 参与者 | 报名参加活动、上传照片、取消报名 | 信息清晰、报名简单、状态可查 | 用户前台 /events：活动列表、详情、报名、取消报名 |
| 现场工作人员 | 活动日签到核销 | 快速核销不排队 | /checkin/:eventId 签到页 |
| 供应商/协作方 | 内部合作供应商、外部服务商、活动协助人员 | 清楚分工与任务 | 内部合作供应商、外部服务商、活动协助人员管理（○ 待补） |

### 2.2 用户关键场景（User Story）

| 编号 | 角色 | 用户故事 | 验收关注点 |
|---|---|---|---|
| US-1 | 管理员 | 作为管理员，我输入房源编码就能带出房源信息，确认后一键生成活动 | 带出信息准确、确认后可修改 |
| US-2 | 管理员 | 作为管理员，我在后台能按活动查看报名列表，一键通过/驳回并自动通知 | 通知必达、驳回有理由 |
| US-3 | 参与者 | 作为参与者，我选时段、填表单、提交报名，能知道审核结果 | 表单字段清晰、结果可查 |
| US-4 | 参与者 | 作为参与者，我计划有变时能取消报名，释放名额 | 取消后名额实时回收 |
| US-5 | 现场人员 | 作为现场人员，我扫码或输手机号就能核销签到，实时看到到场数 | 双通道可用、核销实时 |
| US-6 | 管理员 | 作为管理员，会后我一眼看到报名数、签到率、人均浏览量并导出报表 | 口径一致、导出可用 |
| US-7 | 管理员 | 作为管理员，活动前我用 AI 筹备助手诊断筹备缺口 | 诊断有依据、可执行 |

## 3. 产品总览

### 3.1 功能地图

```
OpenHouse 活动管理系统（v24）
├── 管理员后台 /admin/*
│   ├── 活动管理            ★ 核心（创建/编辑/发布/下线 + 房源集成）
│   ├── 活动筹备
│   │   ├── 报名管理
│   │   └── 审核列表        ★ 核心（通过/驳回 + 自动通知）
│   ├── 现场管理
│   │   ├── 签到管理        ★ 核心（二维码/手机号）
│   │   └── 实时动态
│   ├── 会后管理
│   │   ├── 数据统计        ★ 核心（get_event_statistics + ECharts）
│   │   └── 活动报告
│   ├── 活动场次管理        ○
│   ├── 活动全局概览        ○
│   ├── 内部合作供应商      ○
│   ├── 外部服务商          ○
│   └── 活动协助人员管理    ○
├── 用户前台 /events/*
│   ├── 活动列表 / 活动详情
│   ├── 在线报名 / 取消报名
│   └── 活动照片上传 / 活动相册链接（☆ 后续迭代引入）
├── 签到页 /checkin/:eventId  ★ 核心
└── AI 筹备助手（前台浮窗）    ★ v24 实测
```

> 后台 9 个主菜单为 v2 交付（★ 实测对话原文），默认展开活动筹备、现场管理、会后管理三个分组，支持展开/收起与当前页高亮。

### 3.2 活动全生命周期（主流程）

```
【① 创建】输入房源编码/链接 ──贝壳房源技能──► 带出房源信息
            （小区/面积/挂牌价/居室/户型/楼层/位置）
                    │ 人工确认「是这套房源」
                    ▼
            填充活动表单：标题=房源标题 · 地点=行政区+商圈
            · 描述=户型/面积/楼层/价格 · 时间/名额/参观路线/报名字段
        ↓
【② 发布】活动上线（/events 前台可见）——支持编辑、下线
        ↓
【③ 报名】参与者提交自定义表单（姓名/电话/单位/人数/预约时段）
        ↓
【④ 审核】管理员在审核列表 通过/驳回 ──触达平台──► 自动发送通知
        ↓
【⑤ 签到】活动日：签到二维码 · 扫码签到 / 手机号签到 → 实时核销
        ↓
【⑥ 复盘】get_event_statistics() 聚合：报名人数/签到率/到访率/人均浏览量
            → ECharts 可视化 → 导出报表 → 照片归档/相册链接
```

**活动状态（events.status，☆ 推断补全）**

```

 └───┬────┘          └───┬────┘             └────────┘
     │ 编辑               │ 下线
     ▼                   ▼
 （回到编辑态）        ┌────────┐
                      │ 已下线  │
                      └────────┘
```

**报名状态（registrations.status，☆ 推断补全）**

```
 ┌────────┐   通过    ┌────────┐   扫码/手机号签到   ┌────────┐
 │ 待审核  │ ───────► │ 已通过  │ ─────────────────► │ 已签到  │
 └───┬────┘          └───┬────┘                    └────────┘
     │ 驳回               │ 活动日未到
     ▼                   ▼
 ┌────────┐           ┌────────┐
 │ 已驳回  │           │ 未到访  │（爽约）

```

> **★ 实测依据**：v1 需求原文明确"通过/驳回""扫码签到、手机号签到、实时核销""签到率"；完整状态枚举与字段需研发确认（见附录 Q2）。

### 3.4 平台架构（承载层）

与颜选好房派单系统同构：MOMA 平台壳（对话工作台 + 预览 + 版本管理）→ Agent Runtime（文件编辑/命令执行/构建验证/Supabase execute_sql/技能调用）→ Supabase 数据层 + 平台技能层。

**本应用挂载的 7 个技能（★ 实测）**：贝壳房源、贝壳单点登录、定时任务、S3存储、触达平台、数据查询、通用大模型。

| 数据查询 | 统计取数 |
| 通用大模型 | AI 筹备助手 |

## 4. 功能需求详述

> 每条需求给出「需求描述 / 前置条件 / 交互与规则 / 异常与边界 / 验收标准」。优先级 P0（必须有）、P1（应该有）、P2（可以有）。

### 4.1 活动管理域

#### FR-1.1 活动创建（含房源集成）★

| 项 | 内容 |
|---|---|
| 优先级 | P0 |
| 状态 | 已上线（v1 创建 + v5 房源集成）★ |

**需求描述**：管理员创建开放日活动，设置时间、地点、名额、参观路线与报名字段；支持通过房源编码自动带出房源信息。

**交互与规则（★ 实测 v5 交付）**
1. **房源编码输入**：支持房源 ID（如 `12345`）与房源链接（如 `https://xa.lianjia.com/zufang/12345.html`）两种输入。
2. **查询与确认**：点击"查询房源"→ 弹出确认对话框，展示**小区名称、面积、挂牌价格、居室、户型、楼层、位置** → 人工点击"确认使用"确认是这套房源。
3. **自动填充**：活动标题 = 房源标题；活动地点 = 行政区 + 商圈；活动描述 = 户型、面积、楼层、价格等详细信息。
4. **可修改**：已确认房源信息固定显示在表单顶部，所有字段可随时人工修改。
5. 活动字段：时间、地点、名额、参观路线、自定义报名表单字段。

**异常与边界**
- 房源编码/链接无效 → 明确报错，不得填充旧数据。
- 接口返回字段类型异常（实际发生：API 返回 string，代码预期 number）→ 类型适配层统一转换（v5 中 Agent 已自主修复此类问题）★。
- 同一房源重复创建活动 → 建议提示已有在途活动（☆ 建议）。

**验收标准**
1. 合法房源编码 100% 带出信息；带出字段与房源系统一致。
2. 确认前不写入任何表单字段；确认后所有字段仍可修改。
3. 活动创建后在前台 /events 可见（发布后）。

#### FR-1.2 活动编辑与删除

**需求描述**：对活动信息进行修改或删除。

**规则**
1. 草稿态可编辑全部字段；已发布活动编辑后即时生效（☆ 建议二次确认）。
2. 删除需二次确认；**已有报名的活动不建议物理删除，建议下线**（保护报名数据，☆ 建议）。
3. 所有变更留痕（☆ 建议接入更新日志，对齐颜选好房系统实践）。

#### FR-1.3 活动发布与下线

**需求描述**：控制活动的可见性。

**规则**
1. 发布后前台 /events 列表可见，参与者可报名。
2. 下线后前台不可见、不可报名，已产生的报名与签到数据保留。
3. 发布前校验：时间、地点、名额必填（☆ 建议增加名额 > 0 校验）。

### 4.2 报名域

#### FR-2.1 自定义报名表单 ★

| 项 | 内容 |
|---|---|
| 优先级 | P0 |
| 状态 | 已上线（v1）★ |

**需求描述**：参与者在线提交报名，表单支持自定义字段。

**字段（★ 实测 v1 需求原文）**：姓名、电话、单位、人数、预约时段。

**规则**
1. 管理员创建活动时可配置表单字段（v1 内置五类字段；"更复杂的报名表单自定义"列入后续迭代，见 v1 Agent 规划原文）。
2. 电话字段需格式校验；预约时段需在活动时间范围内。
3. 报名提交后进入待审核状态。
4. **名额控制**：报名人数（含随行人数）累计不得超过活动名额（☆ 建议明确超额策略：硬截止 or 候补）。

**异常与边界**
- 重复报名（同人同活动）→ 拦截并提示。
- 活动下线/名额已满时 → 关闭报名入口。

#### FR-2.2 取消报名

**需求描述**：参与者可取消自己的报名（★ 会话中明确出现"取消报名（参与者视角）"需求）。

**规则**
1. 仅可取消本人报名。
2. 已审核通过的取消 → 名额实时释放。
3. 已签到的不可取消（☆ 建议）。

### 4.3 审核与通知域

#### FR-3.1 报名审核 ★

| 项 | 内容 |
|---|---|
| 优先级 | P0 |
| 状态 | 已上线（v1）★ |

**需求描述**：管理员后台按活动查看报名列表，逐条通过/驳回。

**规则**
1. 审核列表展示：报名人、电话、单位、随行人数、预约时段、提交时间、状态。
2. 通过 → 名额占用生效；驳回 → 需填写驳回理由（☆ 建议，作为通知内容）。
3. 支持批量审核（○ 待确认是否已实现）。
4. 审核结果**自动发送通知**（v1 需求原文"自动发送通知"，通道推测为触达平台技能 ☆）。

**验收标准**
1. 审核动作后报名状态即时更新。
2. 通知触达率可统计（联动 8.2 指标树）。

### 4.4 签到域

#### FR-4.1 签到与核销 ★

| 项 | 内容 |
|---|---|
| 优先级 | P0 |
| 状态 | 已上线（v1）★ |

**需求描述**：活动日现场签到，实时核销。

**规则（★ 实测 v1 交付）**
1. **签到二维码**：系统按活动生成签到二维码（qrcode 库实现 ★）。
2. **双通道签到**：扫码签到 + 手机号签到（现场人员输入手机号代核销）。
3. **实时核销**：签到即写入 check_ins 表，现场管理页实时动态可见到场数。
4. 签到页路由 `/checkin/:eventId`，独立于前台后台，适合现场平板/手机使用。

**异常与边界**
- 重复扫码 → 幂等处理，提示已签到。
- 未通过审核的人员扫码 → 拒绝并提示。
- 离线场景（现场网络差）→ ○ 待确认是否有离线补偿方案（建议列入 V2.0）。

### 4.5 数据统计域

#### FR-5.1 活动数据统计与报表 ★

| 项 | 内容 |
|---|---|

## 5. AI Agent 设计

### 5.1 系统中的 AI 能力清单

| 编号 | 能力 | 工作模式 | 是否 Agent | 证据 |
|---|---|---|---|---|
| AI-1 | 对话构建 Agent | 平台级 ReAct：读代码→改代码→查库→构建验证 | ✅（平台级） | ★ v1–v5 步骤流 |
| AI-2 | 贝壳房源查询 | Agent 自主调用贝壳房源技能，结果人工确认后填充 | 技能调用 + 人工确认 | ★ v5 |
| AI-3 | AI 筹备助手 | 前台浮窗"点我诊断筹备进度" | ○ 待确认（入口实测，实现未知） | ★ v24 |
| AI-4 | 自动通知 | 审核通过/驳回触发 | ✍️ 动作类（推测走触达平台） | ★ v1 需求原文 |

### 5.2 AI 筹备助手设计（v24 入口 → Agent 化方案）

**现状**：前台浮窗入口（★ 实测），内部实现 ○ 待确认。

**Agent 化目标形态**（沿用平台方法论"场景 → 封装工具 → AI 自主调用"）：

```
用户点击「AI筹备助手，点我诊断筹备进度」
        │
        ▼
  意图判断（LLM 自主决策）
        │
  ┌─────┴──────────────────────┐
  │ 并行调用只读查询工具：         │
  │ T-1 活动信息完整度（必填项缺失）│
  │ T-2 报名进度（报名数 vs 名额） │
  │ T-3 审核积压（待审核条数/时长） │
  │ T-4 签到物料就绪度（二维码状态）│
  │ T-5 供应商协作就绪度           │
  └─────┬──────────────────────┘
        ▼
  生成诊断报告：整体就绪度评分 + 风险清单 + 待办建议
```

**新增工具（待开发）**
| 工具 | 类型 | 说明 |
|---|---|---|
| T-1 查询活动信息完整度 | 读 | 校验必填字段缺失 |
| T-2 查询报名进度 | 读 | 报名数/名额/时段分布 |
| T-3 查询审核积压 | 读 | 待审核数、最老待审时长 |
| T-4 查询签到就绪 | 读 | 二维码生成状态、签到配置 |
| T-5 查询协作就绪 | 读 | 供应商/协助人员到位情况（○ 依赖 FR-6.2） |

**设计原则**：首期全部**只读**——诊断与建议由 AI 生成，**执行动作（催办、补通知）必须人工确认**，与颜选好房系统"写操作需人工确认"原则一致。

### 5.3 房源集成的 Agent 模式（v5 的方法论价值）

v5 的实现过程本身就是教材（★ 实测）：

1. Agent 先**调用技能了解接口规范**（Used a skill：贝壳找房）；
2. 自主发现**类型不匹配**（API 返回 string，代码预期 number），修正 EventForm 与 HouseInfo 类型定义；
3. 自主修复构建错误（模板字符串、CSS @import 位置）直至构建通过；
4. 交付时明确人机边界：**自动带出 → 人工确认 → 才填充**。

**沉淀为模式**：外部数据技能接入业务表单时，必须经过"查询 → 展示 → 人工确认 → 写入"四步，禁止静默写入。

### 5.4 Agent 边界原则

| 原则 | 内容 |
|---|---|
| 原则一 | 能用规则解决的不用 AI（名额校验、时段校验是纯规则） |
| 原则二 | AI 用于"不确定"处：诊断、归因、自然语言生成 |
| 原则三 | 对外能力只读优先，写操作（通知、状态变更）需人工确认 |
| 原则四 | 不混淆概念：明确区分"AI 能力调用"与"AI Agent"（对齐颜选好房系统的诚实边界实践） |

## 8. 指标体系与埋点

### 8.1 北极星指标

> **北极星指标：活动到访率（签到率）**
> = 活动当日签到去重人数 ÷ 审核通过人数

**选择理由**：初始需求明确要"报名人数、签到率"（★ v1 原文），到访率是开放日活动的最终兑现——它串联报名质量（表单真实性）、审核质量（驳回是否有效）、活动吸引力（是否值得到场）、通知触达（是否知道时间地点）。到访率下降时，可沿指标树逐层下钻定位。

### 8.2 指标树

```
活动到访率（北极星）
├── ① 活动供给域
│   ├── 活动创建数 / 发布数 / 下线数
│   ├── 场均名额 · 名额利用率（报名/名额）
│   └── 房源活动占比（v5 集成后经房源创建的活动比例）
├── ② 报名漏斗域
│   ├── 活动页 PV / UV
│   ├── 报名提交数 · 报名率（提交/PV）
│   ├── 人均浏览量（详情 PV/UV，★ 会话需求原文）
│   └── 预约时段分布（引导分流的依据）
├── ③ 审核效率域
│   ├── 待审核存量 · 审核时长（中位/P90）
│   ├── 通过率 · 驳回理由 TOP 分布
│   └── 通知触达率（触达平台回执）
├── ④ 签到履约域
│   ├── 签到率（北极星）· 爽约率（通过未到访）
│   ├── 扫码 vs 手机号签到占比
│   ├── 开场 30 分钟签到集中度（现场承载预警）
│   └── 核销时效
├── ⑤ 会后资产域
│   ├── 报表导出次数 · 统计页渗透率
│   ├── 照片上传量 · 相册链接打开次数（☆ 需埋点）
│   └── 活动报告生成数（○ V2.0）
└── ⑥ AI 效果域
    ├── AI 筹备助手打开率 · 诊断次数/活动
    ├── 诊断建议采纳率（待办完成率）
    ├── 房源查询成功率（v5）· 带出信息确认率（确认 vs 修改比例）
    └── AI 调用成本与延迟
```

### 8.3 埋点事件表（☆ 建议）

| 事件名 | 触发时机 | 关键属性 | 用途 |
|---|---|---|---|
| `event_created` | 活动创建 | event_id, 是否房源带入, 创建耗时 | 创建效率 |
| `house_lookup_submitted` | 提交房源查询 | 输入类型（ID/链接）, 成功/失败 | v5 功能质量 |
| `house_confirm_accepted` | 确认使用房源 | 修改字段数（0=直接采信） | 人机协同质量 |
| `event_published / event_offline` | 发布/下线 | event_id, 状态时长 | 供给监控 |
| `registration_submitted` | 提交报名 | event_id, 字段完整度, 时段 | 漏斗 |
| `registration_approved / rejected` | 审核 | event_id, 审核时长, 理由 | 审核效率 |
| `notice_sent / notice_delivered` | 通知发送/送达 | 通道, 回执状态 | 触达率 |
| `registration_cancelled` | 取消报名 | event_id, 状态, 距活动开始时长 | 名额回收 |
| `checkin_success` | 签到成功 | channel, 距开场时间, 排队时长 | 现场履约 |
| `checkin_blocked` | 签到被拒 | 原因（未通过/重复） | 异常监控 |
| `stats_viewed / report_exported` | 查看统计/导出 | event_id, 指标项 | 会后渗透 |
| `album_link_opened` | 相册打开 | event_id, 来源 | 传播 |
| `ai_assistant_opened` | 打开 AI 筹备助手 | event_id, 筹备阶段 | AI 渗透 |
| `ai_diagnosis_generated` | 生成诊断 | 命中工具数, 耗时, 就绪度评分 | AI 效果 |

> **埋点原则**：报名→审核→通知→签到四步必须形成**可贯通的单据级链路**（event_id + registration_id 贯穿），否则到访率无法下钻。

### 8.4 监控与告警

| 监控项 | 阈值（建议） | 方式 |

| 待审核积压 | > 50 条或最老 > 24h | 推送管理员 |

| 签到接口失败率 | > 1% | 即时告警 |
| 通知触达失败率 | > 5% | 即时告警 |
