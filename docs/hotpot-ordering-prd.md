## 1. 项目背景与目标

### 1.1 项目背景

火锅堂食订单通常具有多人共同决策、锅底组合复杂、菜品数量多、规格差异明显、临时加菜频繁等特点。传统纸质菜单或服务员代点容易造成等待时间长、信息确认反复、漏单错单和高峰期服务压力。

本产品围绕“顾客到店后独立完成一桌火锅订单”设计移动端 H5，将就餐人数、锅底配置、菜品选择、优惠使用和订单确认串成连续流程，并在关键节点提供推荐与纠错。

### 1.2 核心问题

| 编号 | 用户问题 | 产品应对 |
|---|---|---|
| P1 | 不同人数适合多少锅底、多少菜不清楚 | 先选人数，并据此承接后续推荐与金额提示 |
| P2 | 单锅、双锅、三锅的组合选择容易出错 | 用分步式锅底配置和实时组合预览降低理解成本 |
| P3 | 菜品多、分类多，寻找效率低 | 分类导航、关键词搜索与推荐菜组合 |
| P4 | 多人点餐时购物车内容容易失控 | 全局购物车、数量调整、清空与金额汇总 |
| P5 | 优惠券、订单备注容易在最后一步遗漏 | 确认页集中处理优惠、备注与附加礼包 |
| P6 | 下单后用户缺少明确反馈 | 独立成功页说明订单状态并推荐继续加菜 |

### 1.3 产品目标

- 让用户在移动端独立完成堂食下单，无需服务员全程介入。
- 把锅底选择从“自由组合难理解”转化为可视化、分步骤配置。
- 降低菜单查找与选择成本，提高从进入点餐到提交订单的完成率。
- 通过购物车、优惠与确认页减少错单、漏单和价格误解。
- 为后续对话式点餐、智能推荐和门店系统对接预留标准化能力。

### 1.4 非目标

- 本期不覆盖外卖配送履约与骑手调度。
- 本期不覆盖商城商品的物流订单。
- 本期不处理真实支付、退款和发票流程。
- 本期不包含后厨排队、出餐叫号和库存采购管理。

## 2. 用户与使用场景

### 2.1 用户角色

| 角色 | 需求 | 主要操作 |
|---|---|---|
| 到店顾客 | 快速完成一桌点餐并确认价格 | 选人数、选锅底、选菜、用券、下单 |
| 同桌顾客 | 共同查看菜品并提出加菜需求 | 浏览菜单、查看购物车、追加菜品 |
| 门店服务员 | 降低重复点单与确认工作 | 协助异常订单、核对订单状态 |
| 门店运营 | 优化菜单、推荐和优惠策略 | 分析漏斗、热销菜、客单价与优惠使用 |

### 2.2 核心用户故事

- 作为到店顾客，我希望先选择就餐人数，以便系统给出更合理的点餐基础。
- 作为偏好不同口味的一桌顾客，我希望选择单锅、双锅或三锅，并自由组合锅底。
- 作为首次到店顾客，我希望看到锅底最佳搭配菜品，减少决策成本。
- 作为点餐用户，我希望按分类或关键词找到菜品，并选择规格和数量。
- 作为订单发起人，我希望随时查看购物车总数和总金额，并能修改或清空。
- 作为价格敏感用户，我希望在提交前选择可用优惠券并确认最终金额。
- 作为已下单用户，我希望明确知道下单是否成功，也能继续加菜。

## 4. 核心业务流程

### 4.1 主流程

```text
进入首页
  → 选择“堂食”
  → 选择就餐人数
  → 选择锅底数量
  → 配置锅底口味
  → 可选：查看最佳搭配菜品
  → 进入菜单
  → 搜索 / 分类浏览 / 查看详情
  → 选择规格与数量
  → 查看购物车
  → 确认订单
  → 填写备注 / 选择优惠券 / 选择礼包
  → 提交订单
  → 下单成功
  → 可选：继续加菜
```

### 4.2 关键分支

- 未选择锅底时，“先加购锅底”按钮不可进入下一步。
- 锅底数量与所选锅底份数不一致时，不允许继续。
- 菜品存在规格时，点击菜品进入规格选择；规格确认后加入购物车。
- 购物车为空时，不允许进入确认订单。
- 优惠券仅展示当前订单满足门槛的可用权益；不满足时应说明原因。
- 提交订单失败时保留全部已选内容，允许用户重试。

## 5. 功能需求

### FR-1 首页与场景入口

#### FR-1.1 首页展示

- 展示品牌主视觉或轮播区域。
- 展示外卖、堂食、商店三个业务入口。
- 展示首页、点单、我的底部导航。
- 当前所在导航项需具有明确选中态。

#### FR-1.2 堂食入口

- 点击“堂食”进入就餐人数选择页。
- 返回首页时不应创建无效订单。

### FR-2 就餐人数

#### FR-2.1 人数选择

- 支持选择 1–15 人。
- 默认不选择任何人数。
- 每次只允许选择一个人数。
- 选中后进入锅底配置流程。

#### FR-2.2 费用提示

- 页面应展示门店与人数相关的收费说明。
- 当前原型包含自助小料、茶水按人数计费及儿童减免提示。
- 实际计费规则应由门店配置，不在前端写死。

### FR-3 锅底配置

#### FR-3.1 锅底数量

- 支持一份、两份、三份锅底。
- 切换锅底数量时实时更新组合预览和金额。
- 当已选份数超过新锅底数量时，需提示用户确认后再移除多余锅底。

#### FR-3.2 锅底类型

原型包含以下锅底：

| 锅底 | 标识 | 示例价格 |
|---|---|---:|
| 野山菌汤 | mushroom | ¥32 |
| 牛油辣锅 | spicy | ¥32 |
| 藤椒辣锅 | tomato / pepper | ¥32 |

> 锅底名称、图片、价格与上下架状态应由后台配置；标识以实际接口为准。

#### FR-3.3 数量操作

- 点击加号增加该锅底份数。
- 点击减号减少该锅底份数。
- 已选总份数不得超过当前锅底数量。
- 底部按钮实时显示锅底小计。

#### FR-3.4 搭配推荐

- 用户完成锅底选择后可触发“最佳搭配菜品”弹层。
- 弹层展示推荐菜品、价格、规格与快捷选择。
- 用户可选择“待会再说”或确认选中的推荐菜品。
- 推荐结果应与当前锅底、人数和门店在售菜品相关。

### FR-4 菜单浏览

#### FR-4.1 门店与桌台信息

- 菜单页展示当前门店名称。
- 展示桌号与就餐人数。
- 信息错误时用户可返回上一步修改。

#### FR-4.2 搜索

- 支持按菜品名称关键词搜索。
- 输入过程中实时过滤结果。
- 无匹配结果时展示空状态与清除搜索入口。

#### FR-4.3 分类导航

原型包含肉类、蔬菜、豆类、海鲜、菌菇、甜品、主食、饮料、酒水等分类。

- 左侧分类与右侧菜品列表联动。
- 点击分类滚动到对应分组。
- 用户滚动菜品列表时同步高亮当前分类。

#### FR-4.4 菜品卡片

- 展示菜品图片、名称、价格、计价单位和数量控件。
- 售罄菜品不可加购，并展示售罄状态。
- 已选菜品在卡片上显示当前数量。

#### FR-4.5 菜品详情

- 点击菜品进入底部详情面板。
- 展示大图、名称、描述、价格与规格。
- 支持小份、大份等互斥规格选择。
- 未选择必选规格时，不允许加入购物车。

### FR-5 购物车

#### FR-5.1 购物车入口

- 底部固定栏展示已选菜品数量、总金额与下一步按钮。
- 购物车为空时按钮不可用。

#### FR-5.2 购物车面板

- 展示已选菜品、规格、单价、数量与小计。
- 支持增加、减少和删除单项。
- 支持清空全部菜品，清空前需二次确认。
- 修改后实时同步菜单卡片和总金额。

### FR-6 订单确认

#### FR-6.1 订单商品

- 展示锅底与菜品明细。
- 支持最后一次修改数量。
- 展示商品总数与应付金额。

#### FR-6.2 订单备注

- 支持填写口味、忌口、上菜顺序等备注。
- 限制最大字数并过滤不支持的字符。

#### FR-6.3 优惠券

- 展示当前可用优惠券数量与优惠金额。
- 点击进入优惠券选择弹层。
- 优惠券卡片展示使用门槛、优惠内容、有效状态与选择框。
- 单笔订单默认只允许选择一张互斥优惠券。
- 选择后实时更新应付金额。

#### FR-6.4 优惠券礼包

- 支持勾选购买优惠券礼包。
- 清晰展示礼包价格与包含权益。
- 礼包费用计入应付金额。

#### FR-6.5 提交订单

- 按钮展示最终应付金额。
- 防止重复点击造成重复订单。
- 提交过程中展示加载状态。
- 成功后清理当前草稿并跳转成功页。
- 失败时保留草稿并提示重试。

### FR-7 下单成功与加菜

#### FR-7.1 成功反馈

- 明确展示“下单成功”。
- 说明后厨正在准备菜品。
- 若订单处理中，应提供状态查询入口。

#### FR-7.2 推荐加菜

- 展示与当前锅底和已点菜品互补的推荐。
- 支持一键加菜并创建追加订单或合并到当前桌台订单。
- 已下单菜品不应重复高频推荐。

## 6. 交互与状态规则

### 6.1 订单草稿状态

```text
未开始 → 已选人数 → 已选锅底 → 已选菜品 → 待确认 → 提交中 → 已下单
```

- 用户返回上一步时保留已选内容。
- 刷新或短暂退出后应尽可能恢复未提交草稿。
- 门店、桌台或就餐方式变化时，应提示是否清空原草稿。

### 6.2 金额规则

```text
商品金额 = 锅底金额 + 菜品金额
优惠金额 = 满减券等可用优惠合计
附加金额 = 小料 / 茶水 / 优惠礼包等费用
应付金额 = 商品金额 + 附加金额 - 优惠金额
```

- 所有金额统一使用分为最小计算单位。
- 前端金额仅用于展示，最终金额以后端校验为准。
- 价格变化时提交前必须提示用户重新确认。

### 6.3 异常状态

| 场景 | 处理方式 |
|---|---|
| 菜品售罄 | 禁止加购并标记售罄 |
| 菜品价格变化 | 确认页提示并要求重新确认 |
| 优惠券失效 | 自动取消选择并说明原因 |
| 网络中断 | 保留草稿，恢复网络后重试 |
| 重复提交 | 使用订单幂等标识拦截 |
| 桌台失效 | 阻止下单并提示联系服务员 |

## 7. 数据模型

### 7.1 核心实体

| 实体 | 关键字段 |

| 门店 Store | store_id、name、status、service_rules |
| 桌台 Table | table_id、store_id、table_no、status |

| 订单项 OrderItem | order_item_id、order_id、item_type、sku_id、quantity、price |

### 7.2 数据一致性

- 提交订单时重新校验商品状态、规格、价格、库存和优惠券。
- 订单快照保存下单时的名称、价格和规格，避免菜单更新影响历史订单。
- 草稿和正式订单使用不同状态，未提交草稿不进入后厨履约。

## 8. 对话式能力

产品可向 AI 助手或其他智能入口提供受控工具，使用户通过自然语言完成点餐配置。

### 8.1 读取当前订单

工具能力：读取当前就餐人数、锅底、购物车数量与金额，不修改订单。

典型问题：

- “我现在点了什么？”
- “一共多少钱？”
- “我们选了几个锅底？”

### 8.2 一键配置订单

工具能力：一次设置就餐人数、锅底和菜品，并自动打开点餐区域供用户继续确认。

约束：

- 就餐人数范围为 1–15 人。
- 锅底至少选择 1 种，最多选择 3 种。
- 菜品必须来自门店当前可售列表。
- AI 只能配置草稿，不得绕过确认直接提交正式订单。

### 8.3 安全边界

- AI 不得擅自提交订单或产生支付。
- 推荐需明确区分“建议”与“已加入购物车”。
- 涉及过敏原、忌口和儿童用餐时，仅做信息提示，不替代用户判断。
- 所有工具调用都需返回明确成功或失败状态。

## 9. 非功能需求

### 9.1 性能

- 首屏在常见移动网络下应快速可交互。
- 菜单列表滚动保持流畅，图片采用懒加载与合适尺寸。
- 购物车与金额更新应即时反馈。

### 9.2 可用性

- 适配常见手机尺寸和安全区域。
- 核心按钮固定在拇指易触达区域。
- 选中、不可用、加载、错误和成功状态必须视觉可辨。
- 弹层支持明确关闭，不依赖点击遮罩作为唯一退出方式。

### 9.3 无障碍

- 按钮、数量控件和规格选择提供可识别标签。
- 文字与背景满足基本对比度要求。
- 不仅依赖颜色表达售罄、选中或错误状态。

### 9.4 安全与隐私

- 不在前端存储支付凭证或敏感身份信息。
- 接口校验门店、桌台与订单归属。
- 订单提交接口具备幂等、防刷与频率限制。

## 10. 指标与埋点

### 10.1 核心漏斗

```text
进入堂食 → 选择人数 → 完成锅底 → 加入首道菜 → 进入确认页 → 提交成功
```

### 10.2 核心指标

| 指标 | 定义 |
|---|---|
| 堂食点单完成率 | 成功下单人数 / 进入堂食人数 |
| 锅底配置完成率 | 完成锅底人数 / 进入锅底页人数 |
| 首道菜加购率 | 加入至少一道菜人数 / 进入菜单人数 |
| 订单提交成功率 | 成功订单数 / 提交尝试数 |
| 平均点单时长 | 进入堂食到成功下单的平均时长 |
| 客单价 | 成功订单应付金额 / 成功订单数 |
| 推荐采纳率 | 加购推荐菜用户数 / 查看推荐用户数 |
| 优惠券使用率 | 使用优惠券订单数 / 成功订单数 |
| 加菜率 | 成功页继续加菜订单数 / 成功订单数 |

## 11. 验收标准

### 11.1 主流程验收

- 用户可从首页进入堂食并选择 1–15 人。
- 用户可选择一至三份锅底，并组合不同口味。
- 未完成锅底配置时不能进入菜单。
- 用户可按分类浏览、搜索菜品、查看详情和选择规格。
- 菜品数量、购物车数量和金额始终一致。
- 用户可在确认页填写备注并选择可用优惠券。
- 重复点击下单不会产生重复订单。
- 成功页能明确反馈下单结果并支持继续加菜。

### 11.2 对话式能力验收

- 能准确读取当前人数、锅底、菜品数量和金额。
- 能按允许范围配置人数、锅底和菜品草稿。
- 非法锅底或菜品标识返回可理解的错误信息。
- 对话式配置后，页面状态与工具返回结果一致。
- 未经用户确认不得直接提交订单。

### 11.3 移动端验收

- 常见手机宽度下无横向溢出。
- 底部操作栏不被系统安全区遮挡。
- 弹层、购物车和优惠券列表可正常滚动。
- 弱网或请求失败时有反馈且不会丢失草稿。

## 12. 风险与后续规划

### 12.1 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 菜单与库存不同步 | 用户选到不可售菜品 | 提交时二次校验并实时同步状态 |
| 优惠规则复杂 | 金额争议 | 统一优惠计算服务并展示明细 |
| 多人同时操作同桌订单 | 数量覆盖或重复 | 引入版本号、合并策略和操作日志 |
| 推荐不准确 | 降低信任 | 基于锅底、人数、历史偏好和在售状态推荐 |
| 高峰期接口拥堵 | 下单失败 | 缓存菜单、限流、重试与降级 |

### 12.2 后续规划

- 多人协同点餐与同桌实时同步。
- 基于人数和已点菜品的数量建议。
- 过敏原、忌口和辣度偏好管理。
- 菜品库存、后厨排队和预计上菜时间展示。
- 桌台二维码自动识别门店与桌号。
- 支付、会员积分、发票和退款闭环。
- AI 点餐助手支持自然语言推荐、预算约束和一键配菜。
