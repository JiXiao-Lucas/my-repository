## 1. 背景与目标

### 1.1 业务背景

颜选好房以**房源视频**作为线上呈现的核心载体。房源要获得视频展示位，必须有人**上门拍摄**。于是产生一条稳定的业务链条：

> 房源维护人提交拍摄需求 → 生成拍摄订单 → 订单进入抢单池 → 经纪人自主抢单 → 预约上门 → 拍摄并上传 → 视频质量审核 → 完成归档 / 返工

链条上每一环都牵扯三类人：**提需求的维护人**、**干活的经纪人**、**管全局的管理者**。链条越长，信息越容易断在某一环——本系统要解决的正是这条链条上的**信息流转效率**与**履约确定性**问题。

### 1.2 现状问题（痛点 → 需求来源）

| 编号 | 痛点 | 业务影响 | 对应需求 |
|---|---|---|---|
| P1 | 订单依赖人工分派，分派靠"喊人"，效率与公平性难兼顾 | 派单周期长，经纪人接单意愿分化 | FR-2.1 抢单地图 |
| P2 | 订单状态散落在多个页面，查一个答案要翻 4–5 个页面 | 管理者与经纪人时间被大量消耗在"找信息"上 | FR-6.1 智能问答 |
| P3 | 抢单池信息不透明，长期无人抢的订单沉底，缺乏显性预警 | 高价值房源视频长期缺位，影响线上转化 | FR-2.1 逾期标黄标红 |
| P4 | 视频质量依赖人工审核，成本高、口径不统一 | 质检人力随单量线性增长 | FR-4.1 视频质量 AI 预审 |
| P5 | 系统里的 AI 只会"问答"和"打分"，不能替人办事 | AI 停留在"能力调用"，未形成生产力 | 第 5 章 Agent 设计 |

> **痛点来源**：P1/P3（抢单机制与逾期预警）来自系统迭代记录；P2/P5 来自 v191 对话中 Agent 对系统的自查评估原文——"信息分散在多个页面"被明确认定为当前系统核心痛点。

### 1.3 产品目标

| 层级 | 目标 | 衡量指标 | 目标值 | 说明 |
|---|---|---|---|---|
| 业务 | 缩短订单从生成到完拍的周期 | 订单 7 日完拍率 | 基线待补（TBD） | 北极星指标，见 8.1 |
| 业务 | 降低长期滞留订单 | 超 30 天未抢单订单占比 | ≤ 5%（TBD） | 需先取近 3 个月基线 |
| 用户 | 降低信息获取成本 | 单次信息查询所需操作步骤 | 由 4–5 步降至 1 步 | 由智能问答承接 |
| 用户 | 提升抢单决策质量 | 抢单池曝光 → 抢单转化率 | 环比提升 | 地图化曝光带来 |
| AI | 让 AI 能回答真实数据问题 | 数据类问题工具调用成功率 | ≥ 90% | v189 已落地，需建监控 |
| AI | 抑制 AI 幻觉 | 数据类回答的人工纠错率 | ≤ 2% | 关键信任指标 |

> **目标值说明**：本系统为内部业务系统，多数指标缺少历史基线。**建议在本次立项时同步补取近 3 个月基线**，再回填目标值——没有基线的目标不具备管理价值。

### 1.4 非目标（本期明确不做）

- 不做佣金结算与费用核算（由财务/结算系统承担）
- 不做视频的底层存储、转码与 CDN 分发（由媒体中台承担）
- 不做经纪人绩效考核与职级体系
- 不做房源信息的原始录入与维护（由房源主数据系统承担）

## 2. 用户与角色

### 2.1 角色定义

| 角色 | 角色说明 | 核心诉求 | 主要使用模块 |
|---|---|---|---|
| 房源维护人 | 提交房源拍摄需求，对自己房源的拍摄进度负责 | 我的房源什么时候能拍完 | 维护人上传记录、我的订单（我维护的） |
| 抢单经纪人 | 自主抢单、预约、上门拍摄、上传视频 | 附近有什么单可抢、我干得怎么样 | 抢单地图、我的订单（我抢的）、智能问答 |
| 城市 / 区域管理者 | 监控派单、抢单、拍摄全景，处理滞留订单 | 一眼看清哪块卡住了 | 拍摄统计汇总、地图分布、抢单记录、更新日志 |
| 质检 / 审核人员 | 视频质量把关 | 哪些视频不合格、为什么 | 视频质量 AI 预审 |
| 系统管理员 | 配置节点、权限、经纪人 | 谁能看什么、流程怎么走 | 经纪人管理、节点管理、权限管理 |

### 2.2 用户关键场景（User Story）

| 编号 | 角色 | 用户故事 | 验收关注点 |
|---|---|---|---|
| US-1 | 维护人 | 作为维护人，我提交房源拍摄需求后，能随时查到"拍到哪一步了" | 状态可查、无需追问运营 |
| US-2 | 经纪人 | 作为经纪人，我打开地图就能看到附近有哪些单可抢、哪些是"急单" | 地图点位可辨识、逾期有颜色预警 |
| US-3 | 经纪人 | 作为经纪人，我用一句话就能问"这个月我完成了几单" | 回答准确、有真实数据支撑 |
| US-4 | 管理者 | 作为管理者，我一眼就能定位"哪些订单已经 60 天没人抢了" | 红标订单可集中查看与跟进 |
| US-5 | 质检员 | 作为质检员，AI 先帮我筛一遍，我只复核高风险视频 | 预审结论可解释、可按维度看 |

## 4. 功能需求详述

> **阅读说明**：每条需求给出「需求描述 / 前置条件 / 交互与规则 / 异常与边界 / 验收标准」五要素。优先级采用 P0（必须有）、P1（应该有）、P2（可以有）。

### 4.1 订单管理域

#### FR-1.1 维护人上传记录

| 项 | 内容 |
|---|---|
| 优先级 | P0 |
| 状态 | 已上线 ★ |

**需求描述**：房源维护人通过本模块提交房源拍摄需求，系统据此生成拍摄订单。

**交互与规则**
1. 支持单条录入与批量上传（☆ 批量上传形式待确认，可能为 Excel 模板导入——系统已挂载「Excel 数据同步」技能）。
2. 必填字段建议：房源编号、楼盘名称、产权交易时间、拍摄类型。
3. 提交后系统生成订单，订单 ID 全局唯一（实测为递增数字，如 11610、5690）。
4. 上传记录可在本模块回溯查询（谁在什么时候传了哪些房源）。

**异常与边界**
- 房源编号重复提交 → 应拦截并提示"该房源已有在途订单"。
- 房源编号不存在于房源主数据 → 应阻塞或标记异常单。

**验收标准**
- 上传成功后，订单在「订单管理」与「抢单地图」中同时可见，延迟 ≤ 5 秒。

#### FR-1.2 订单管理列表

| 项 | 内容 |
|---|---|
| 优先级 | P0 |
| 状态 | 已上线 ★ |

**需求描述**：面向管理者与运营的订单全量管理入口，支持筛选、检索与行内操作。

**列表字段（★ 实测，来自「我的订单」同构表头）**

| 字段 | 说明 | 备注 |
|---|---|---|
| 记录 ID | 订单唯一标识 | 数字递增 |
| 楼盘名称 | 房源所在楼盘 | — |
| 房源编号 | 房源主数据编号 | 如 106129279343 |
| 维护人 | 姓名 + 工号 | 格式：马龙(1000000020105758) |
| 拍摄类型 | 拍摄类型分类 | 实测出现 `-`，代表未填 |
| 距离(km) | 经纪人与房源的距离 | 保留 1 位小数，如 7.9 |
| 接单时间 | 抢单成功时间 | 格式 YYYY/MM/DD HH:mm |
| 预计拍摄时间 | 约定的上门时间 | 默认为接单时间 + 3 小时（☆ 推断，待确认） |
| 订单状态 | 待抢单 / 已生效 / 已完成 / 已放弃 / 已失效 | — |
| 拍摄状态 | 待预约 / 已预约 / 拍摄中 / 已完成 / 已放弃 | — |
| 预约成功 | 是否预约成功 | 实测出现 `-` |

**行内操作（★ 实测）**：`明细` / `附件` / `修改` / `复制通知文案`

**交互与规则**
1. 列表默认按接单时间倒序，支持按状态、楼盘、维护人、时间区间筛选。
2. 分页展示，单页条数可配置。
3. 「全部状态」下拉为状态筛选入口。

**验收标准**
- 1000 条订单数据下列表首屏加载 ≤ 2 秒。

#### FR-1.3 订单明细

**需求描述**：点击「明细」查看单笔订单的完整信息与流转记录。

**内容要求**
- 基础信息：房源、楼盘、维护人、拍摄类型
- 流转信息：入池时间、抢单时间、接单人、预约时间、拍摄时间、上传时间
- 关联信息：更新日志、抢单记录、预约记录、视频预审结果
- 距离信息：基于百度地图技能计算

#### FR-1.4 订单附件

**需求描述**：查看与上传订单相关附件（房源图片、视频文件、沟通凭证等）。

**规则**
- 附件存储于对象存储（Supabase Storage）★
- 文件类型与大小限制待补 ○
- 视频附件需与视频质量 AI 预审联动

#### FR-1.5 订单修改

**需求描述**：对订单关键信息进行修正。

**规则**
1. 可修改字段建议：预计拍摄时间、拍摄类型、备注。
2. 不可修改字段：订单 ID、房源编号、接单时间（历史事实不可回溯篡改）。
3. 所有修改必须写入「更新日志」，记录**修改人、修改时间、修改前后值**。

2. 逾期判定与后端计算结果完全一致，误差 0。

## 5. AI Agent 设计

> **本章为文档核心差异章节。** 系统当前处于"有 AI 能力、缺 AI Agent"的阶段，v189 完成了第一次 Agent 化落地。本章既记录现状，也给出 Agent 化的完整设计规范。

### 5.1 现状评估（AI 能力清单）

系统自查结论（★ v191 对话原文）：

> "系统中一共有两处调用了 AI 模型的能力，**都是单次调用，都不构成严格意义上的 AI Agent**。"

| 编号 | AI 能力 | 工作模式 | 是否 Agent | 问题 |
|---|---|---|---|---|
| AI-1 | 智能问答（改造前） | 关键词检索知识库 → 拼接上下文 → 单次流式调用大模型 | ❌ 否 | 只能答"怎么操作"，不能答"现在怎么样" |
| AI-2 | 视频质量 AI 预审 | 视频/订单信息拼 prompt → 单次调用 → 解析 5 维度评分 JSON | ❌ 否 | 只打分，不决策、不执行 |

**技术底座的短板（★ 实测）**
- 底层 `ai_chat.ts` 仅封装 OpenAI 风格 `chat`（非流式）与 `stream_chat`（流式）两个基础接口；
- **不支持 function calling / tool use / 多步 agent loop**；
- `package.json` 未引入任何 Agent 框架（LangChain、AutoGPT 等）；
- 全项目检索无 `tool_choice`、`function_call`、任务规划相关代码。

> **产品结论**：现有底座**无法直接支撑 Agent**，Agent 化必须先补"工具调用层"这一基础设施。这正是 v189 采用自研工具封装路线而非引入框架的原因（☆ 推断）。

### 5.2 智能问答 Agent 设计（v189 已落地）★

| 项 | 内容 |
|---|---|
| 优先级 | P0 |
| 状态 | 已上线（v189 升级 / v190 常用问题 / v186、v188 历史记录） |
| 定位 | 业务操作助手（**名称仍叫"智能问答"，保持用户心智不变**）★ |

#### 5.2.1 双模式路由

```
           用户提问
              │
              ▼
     ┌──────────────────┐
     │  意图判断（LLM）   │  AI 自主决策
     └────────┬─────────┘
              │
     ┌────────┴─────────┐
     │                  │
  "怎么操作"          "现在怎么样"
  知识库类问题          数据类问题
     │                  │
     ▼                  ▼
┌──────────┐    ┌─────────────────────┐
│ 知识库检索 │    │ 工具调用（Tool Use） │
│ (RAG)    │    │ 自主选择 → 执行 → 拼接 │
└────┬─────┘    └──────────┬──────────┘
     │                     │
     └──────────┬──────────┘
                ▼
        流式生成自然语言回答
                │
                ▼
        写入问答历史记录
```

> **★ 实测原文**："遇到操作类问题仍走原有知识库检索方式；遇到涉及真实业务数据的问题时，会**自主判断并调用后台查询工具**获取真实数据后再回答，**不再凭空编造**。"

#### 5.2.2 工具清单（v189 封装的三个只读查询工具）★

| 工具编号 | 工具名称 | 功能 | 入参 | 出参 |
|---|---|---|---|---|
| T-1 | 查询我的订单最新状态 | 返回当前用户相关订单的状态 | userId（会话内隐式） | 订单列表 + 状态 |
| T-2 | 查询某订单当前谁在拍 | 按订单号或楼盘名查拍摄归属 | 订单号 / 楼盘名 | 拍摄人 + 接单时间 |
| T-3 | 查询本月我已完成的抢单数 | 统计本月完成量 | userId + 月份 | 完成单量 |

**设计原则（★ 产品方的核心约束）**
1. **只读优先**：三个工具全部为只读查询，不涉及写操作——**在 Agent 可信度未建立前，写操作必须极其谨慎**。
2. **原子性**：一个工具只做一件事，不做复合查询。
3. **可解释**：工具返回的是原始事实数据，自然语言解释由模型生成，二者分离。

#### 5.2.3 常用问题（v190）★

| 序号 | 常用问题 | 命中工具 |
|---|---|---|
| 1 | 我的订单现在是什么状态？ | T-1 |
| 2 | 某个订单还有谁在拍？ | T-2 |
| 3 | 这个月我完成了几单？ | T-3 |

**规则**：三条常用问题**置于列表最前面**，点击即直接触发对应查询并返回真实结果（★ 实测）。这是**降低 Agent 使用门槛的关键设计**——用户不需要"学会怎么问"。

#### 5.2.4 问答历史记录（v186 / v188）★

- 所有问答（含知识库模式与工具模式）**照常记录进历史记录**。
- 管理员可在**问答页面右上角**查看历史。
- **产品价值**：历史记录是 Agent 效果的**原始数据来源**，可支撑后续的"未命中问题分析 → 补工具/补知识库"闭环。

#### 5.2.5 兜底与安全

| 场景 | 期望行为 |
|---|---|
| 问题超出工具能力范围 | 明确告知"暂无该数据的查询能力"，**必须禁止编造** |
| 工具执行失败 | 返回明确的失败提示，不伪装成"没有数据" |
| 越权查询（查他人订单） | 服务端按 userId 过滤，模型层不做权限判断 |
| 敏感字段（经纪人手机号等） | 输出前脱敏 |

**验收标准**
1. 数据类问题回答准确率 ≥ 90%（抽样 100 例人工核验）。
2. 幻觉率 ≤ 2%（数据类回答中出现库中不存在事实的比例）。
3. 工具调用链路可在日志中完整回溯（谁问的、命中哪个工具、入参、返回值、最终回答）。

### 5.3 视频质量 AI 预审 Agent 化设计

**现状**：单次调用打分（见 FR-4.1）。

**目标形态**：从"打分"升级为"打分 + 决策 + 执行"。

```
上传视频 → AI 预审打分（5 维度）
              │
      ┌───────┴────────┐
    通过              不通过
      │                 │
   标记完成         AI 自主决策：
                  ① 判断不通过严重程度
                  ② 决定是否通知（T-Notify）
                  ③ 决定通知对象与话术
                      │
                      ▼
                调用写工具：发通知 / 标记订单状态
                      │
                      ▼
                多次不通过 → 自动升级给管理员
```

**新增工具（待开发）**
| 工具编号 | 工具名称 | 类型 | 说明 |
|---|---|---|---|
| T-4 | 发送通知 | ✍️ 写 | 企微 / 短信通知经纪人重拍，带具体原因 |
| T-5 | 标记订单状态 | ✍️ 写 | 将订单标记为"待返工" |
| T-6 | 升级至管理员 | ✍️ 写 | 多次不通过时上报 |

> **⚠️ 写操作是风险分水岭**：建议 T-4/T-5 首期采用**"建议 + 人工确认"**模式（Agent 生成动作建议，人在界面上点确认后执行），待准确率稳定后再开放自动执行。**这一条应写入产品原则。**

### 5.4 工具调用层 Roadmap（四类方向）★

系统在 v191 对话中给出了完整的 Agent 化路径，原文方法论：

> **"先明确一个具体问题场景，再把对应的数据查询或操作封装成工具函数，交给 AI 自己判断何时调用，逐步累积。"**

| 方向 | 内容 | 成本 | 契合痛点 | 状态 |
|---|---|---|---|---|
| **方向一** | 智能问答升级为"业务操作助手"：封装只读查询工具，回答真实数据问题 | 低 | P2 信息分散 | ✅ v189 已落地 |
| **方向二** | 智能异常订单诊断：打通更新日志/抢单记录/施工状态，AI 自主决策多步查询链（订单状态→是否可抢→地图分布→历史抢单记录）给出诊断结论 | 低 | P2、P3 | ⏳ 待开发 |
| **方向三** | 视频预审自动化闭环：不通过时 AI 自主决定发企微/短信通知、多次不通过自动升级 | 中 | P4 | ⏳ 待开发 |
| **方向四** | 经纪人自助问答 + 自助操作：答"我还有几天被移除""附近有哪些可抢订单"，并按位置与历史表现推荐 | 中 | P1、P3 | ⏳ 待开发 |

**优先级建议**：方向二 > 方向一延伸 > 方向三 > 方向四，理由见 9.2 的 RICE 打分。

### 5.5 Agent 边界原则（本产品重要设计准则）★

系统 Agent 对"抢单地图 30/60 天标黄标红"需求的答复原文：

> "**这不算 AI Agent 功能。** 这是纯粹的日期计算 + 条件判断（比较天数、看是否有人抢单来决定颜色），全程没有调用 AI 模型、没有自主决策、也没有工具调用链，是常规的业务规则逻辑，跟'智能问答'里那种 AI 自主判断要不要查数据库的机制完全不同。"

**沉淀为产品原则**：

| 原则 | 内容 |
|---|---|
| 原则一 | **能用规则解决的，不用 AI。** 确定性逻辑（日期比较、阈值判断）用代码实现，成本低、可解释、无幻觉风险。 |
| 原则二 | **AI 只用于"不确定"的地方**：自然语言理解、意图判断、多源信息综合、非结构化内容评估。 |
| 原则三 | **不混淆概念**：对外沟通中，明确区分"AI 能力调用"与"AI Agent"，避免用 AI 概念包装普通功能。 |
| 原则四 | **写操作需人工确认**（见 5.3 风险提示），直至准确率稳定。 |

> 这套边界意识是产品可信度的组成部分——**用户知道 AI 什么时候在场、什么时候不在场，才敢依赖它。**

## 8. 指标体系与埋点

> 本章是系统运营与迭代的度量基础。**建议在下次立项时优先补齐基线数据。**

### 8.1 北极星指标

> **北极星指标：订单 7 日完拍率**
> = （订单生成后 7 个自然日内拍摄状态变为"已完成"的订单数） ÷ （同期生成的订单总数）

**选择理由**：该指标串联了派单效率（能否快速被抢）、抢单活跃度（有没有人抢）、履约能力（抢了能不能拍完）、质量（拍完能不能过审，不通过会延长周期）——**是唯一一个"掉了就一定是某个环节出问题"的复合指标**。

### 8.2 指标树

```
订单 7 日完拍率（北极星）
├── ① 派单效率域
│   ├── 订单生成量
│   ├── 抢单池存量（时点值）
│   ├── 平均抢单时长 = AVG(接单时间 - 入池时间)   ← 关注中位数与 P90
│   ├── 抢单成功率 = 抢单成功数 / 抢单请求数
│   └── 平均派单轮次（订单被抢→放弃→再抢的次数）
├── ② 抢单健康度域
│   ├── 黄标订单数 / 黄标率（>30 天未抢占比）
│   ├── 红标订单数 / 红标率（>60 天未抢占比）      ← 核心预警指标
│   ├── 逾期订单清理率（本周清理黄标订单数 / 期初黄标订单数）
│   ├── 活跃抢单经纪人数（周内至少抢 1 单的人数）
│   └── 抢单集中度（Top 10% 经纪人抢单占比）       ← 衡量公平性
├── ③ 拍摄履约域
│   ├── 预约成功率
│   ├── 上门准时率 = 实际拍摄时间符合预计时间±30min 的比例
│   ├── 3 日掉池率 = 超 3 天未完成掉回抢单池的订单数 / 已生效订单数
│   ├── 弃单率 = 已放弃订单数 / 已生效订单数
│   └── 平均完拍时长 = AVG(拍摄完成时间 - 接单时间)
├── ④ 视频质量域
│   ├── AI 预审通过率
│   ├── 一稿通过率 = 一次预审即通过的订单数 / 提交预审订单数
│   ├── 平均返工次数
│   └── 5 维度评分均分与分布（维度定义待补 ○）
└── ⑤ AI 效果域
    ├── 智能问答调用量 / 渗透率（使用人数 / 总活跃人数）
    ├── 数据类问题占比（工具模式 / 总问答量）
    ├── 工具调用成功率
    ├── 回答采纳率（用户未追问/未纠正即离开的比例，☆ 需埋点）
    ├── 未命中问题 TOP 榜（工具无法回答的问题聚类）  ← 迭代输入
    └── AI 成本与延迟（token 消耗、P95 响应时长）
```
